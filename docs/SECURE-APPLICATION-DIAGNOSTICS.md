# Secure Application Diagnostics

## Purpose and event policy

This is the extensible application-level diagnostic sink for Brilina Forge AI. Add event types as production issues are discovered; do not create a new logging table or one-off logging path for each feature.

Capture only actionable events:
- Errors: unexpected exceptions, failed database writes/reads that affect the operation, unavailable bindings/configuration, AI-provider failures, and cleanup failures.
- Warnings: rejected/expired sessions, exhausted retries, significant authorization denials, and degraded-but-recovered behavior.
- Info: a small number of lifecycle milestones needed to correlate a failing workflow (for example, voice-session started/finished).
- Exclude routine page views, normal successful API traffic, full prompts/messages, transcripts, audio, email addresses, IP addresses, cookies, authorization headers, and secrets.

Every event should have a stable event name, UTC timestamp, severity, category/stage, route, status code where applicable, request/correlation ID, and small allowlisted metadata. Add only safe identifiers and numeric/boolean values. Never pass arbitrary provider messages to the diagnostic helper.

## Access and retention

- The diagnostics API calls `requireOwnerAdmin()`; the owner page also verifies AAL2 MFA.
- Database RLS is enabled and table privileges are revoked from `anon` and `authenticated`. Server-side service-role code is the only intended reader/writer.
- The owner can filter unread/new, unresolved, or all recent events; mark an event read/unread; resolve/reopen; and clear application diagnostic records after browser confirmation and a server-checked confirmation header.
- Clearing these rows deletes only records in `public.secure_application_diagnostics`. It does not delete or change native Cloudflare logs.
- Newly inserted events default to unread. The API currently returns the latest 100 records; older events are not shown by the initial interface.

## Add a diagnostic event in future work

1. Reuse `recordSecureDiagnostic` from `lib/secure-diagnostic.ts`.
2. Choose a stable event name and one of `info`, `warning`, or `error`.
3. Include the request ID generated by the route and a stage such as `database_insert`, `provider_call`, or `cleanup`.
4. Include only keys accepted by `SAFE_DETAIL_KEYS`. Extend that allowlist deliberately when a new non-sensitive field is required.
5. Return a generic user-facing message; do not expose internal details.
6. Add a regression test for the event and verify it through the owner diagnostics page after deployment.

## Voice recording incident (2026-10-23)

Supabase showed successful session inserts (HTTP 201), finalization updates (HTTP 200), attempt reservations (HTTP 200), and cleanup deletes (HTTP 204) during the inspected period. Two rows had `stopped_at IS NULL`, but this does not prove the original failure cause. The exact failing Worker invocation was not present in the inspected Supabase REST log evidence. Root cause remains unconfirmed until the updated Worker is deployed and the failure is reproduced or a matching event is captured.

Instrumentation now distinguishes voice transcription configuration, expired-session cleanup, session insertion, finish/update, cancel/delete, session lookup, retry reservation, Workers AI binding, provider result/failure, and post-transcription cleanup.

## Cloudflare telemetry and cost decision

The current `wrangler.jsonc` enables native Workers Observability. Native Workers Logs are the first place to inspect a matching request and exception; they are not automatically copied into Supabase.

As of 2026-10-23, Cloudflare's current documentation states:
- Workers Logs are available on Free and Paid Workers plans. The documented Free allowance is 200,000 log events/day with 3-day retention; Paid includes 20 million/month and 7-day retention, with additional event charges under the current schedule.
- OpenTelemetry log/trace export destinations are **not available on Workers Free** in the current export documentation; Workers Paid includes 10 million events/month before additional event charges. A destination must be configured in the Cloudflare dashboard, then referenced in Wrangler and deployed.
- Logpush usage-based export became available on self-serve Free, Pro, and Business plans for supported datasets, with 25 GB/month included for internal exports and 25 GB/month for external exports; Workers Trace Events Logpush still requires Workers Paid and has separate request-based pricing.
- Tail Workers can consume live Worker events but require a deployed Tail Worker and secure forwarding/storage design; they are not configured by this change.

Therefore, this change does not enable an OpenTelemetry destination or silently add a paid Cloudflare feature. The initial safe path is selective structured diagnostics written directly by the application to Supabase plus native Cloudflare Workers Logs for infrastructure/runtime evidence. Native-log ingestion can be added after a destination and any applicable costs are explicitly selected in Cloudflare.

## Known limitations

- Historical Cloudflare log ingestion into Supabase is not implemented.
- The exact reported recording failure has not yet been reproduced.
- A production deployment and live owner-browser verification are required before calling the feature complete.
